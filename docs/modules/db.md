# @drift/db

**Owner:** P3 (Tanishq Chavan). Reviewer P2. **Status:** M6 — the platform's data model, two migrations and the client.

## What it is

- **Prisma 7** with the `prisma-client` generator and the node-postgres driver adapter (`@prisma/adapter-pg`). There is no native query engine. The generated client is TypeScript in `src/generated/` (git-ignored); `pnpm --filter @drift/db run build` generates and compiles it.
- **Migrations:**
  - `20260930000000_init` (M5), generated from the schema (`prisma migrate diff --from-empty --to-schema`) plus one hand-written part: a trigger that rejects `UPDATE` and `DELETE` on `AuditLog`;
  - `20261002000000_server_runs` (M6), generated with `prisma migrate diff --from-config-datasource --to-schema` against a database at the first migration: run statuses `QUEUED` and `RUNNING`, `RunMode` (`UPLOAD`, `SERVER`), and on `Run` the columns `mode`, `options`, `attempts`, `startedAt`, `errorMessage`. The columns that come from a report (spec hashes, versions, gate, counts, semver) become nullable, because a server-side run has no report until the worker has run.
- **`createDb(connectionString)`** returns a client; the caller owns it. The web app keeps one per process; tests create one per database.
- **`newId(kind)`**: ids are generated by the application as `<prefix>_<24 base-36 characters>` from 120 random bits (`usr_`, `org_`, `run_`, …), so they are safe in URLs and recognisable in logs.

## Model

| Group    | Models                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity | `User` (email, bcrypt `passwordHash`, `tokenVersion`), `Account` (a GitHub identity)                                                                                                                                                                                                                                                                                                                      |
| Tenancy  | `Organization` (`demo` marks a DEMO organisation, M7), `Membership` (OWNER/ADMIN/MEMBER/VIEWER), `Invitation` (SHA-256 of the token, expiry), `Project`, `ApiKey` (SHA-256, prefix, permissions, optional project, `revokedAt`, `expiresAt`, `lastUsedAt`)                                                                                                                                                |
| Runs     | `Run` (idempotency key and request hash, commit, mode, status, options, attempts, parent run for re-runs, error category and message; from the report: spec hashes, versions, gate, counts), `StageExecution` (per attempt, with cache key and hit), `Artifact` (org-scoped storage key by SHA-256; kinds `report-*` and `input-*`), `Change`, `Evidence` (counts and a reference to the report artifact) |
| History  | `Policy` (a project's `drift-policy/v1` document and its hash, M7), `Suppression`, `AuditLog` (append-only), `WebhookDelivery` (for M8)                                                                                                                                                                                                                                                                   |

Rules that hold everywhere:

- every tenant-owned row has `orgId`, and every query in `apps/web/src/server` filters by it;
- no secret is stored: passwords as bcrypt hashes, API keys and invitation tokens as SHA-256;
- `Run` is unique per `(orgId, idempotencyKey)`, which is what makes uploads idempotent even when two requests race.

## Deviations from PLAN

- **No `Session` table.** Sessions are encrypted JWTs (ADR-0007: next-auth v4's credentials provider requires them). `User.tokenVersion` revokes them, and authorisation reads the database on every request.

## Tests

- `ids.test.ts` (unit). The client and the migrations are exercised by the web app's integration tests: the migrations are applied to a fresh Postgres, and `prisma migrate diff` must then find no difference from `schema.prisma`, so the two cannot drift apart.

## Questions an examiner might ask

- **How do you know the audit log is append-only?** The database refuses: a trigger raises on `UPDATE` and `DELETE`. A test tries both through Prisma and both fail.
- **Why hash API keys with SHA-256 and passwords with bcrypt?** A key is 256 random bits: it cannot be guessed, so a fast hash is enough and lets the key be looked up by its hash. A password is chosen by a person and can be guessed, so it needs a slow hash.
- **Why application-generated ids instead of serial ones?** Serial ids reveal how many rows exist and invite guessing; these are random, prefixed by type, and can be created before the row is written (a run id is needed for its child rows in the same transaction).
- **Why are the report columns nullable now?** A server-side run exists before its report: it is queued, then running. Making them nullable is the honest model; the API marks `gate`, `summary` and `semver` optional for the same reason.
- **What stops a schema change without a migration?** The integration setup applies the migrations and then diffs the database against `schema.prisma`; any difference fails the run.
